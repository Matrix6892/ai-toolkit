# Проверка product-engineering · 2026-11-11

Пакет переносит последовательность анализа, а не обещает одинаковый интеллект моделей. Сопоставление с компетенциями курса — в [источниках](../../references/sources.md). Эти материалы нужны для проверки и обслуживания; обычная задача их не загружает.

## Итог

Первая Terra-попытка задачи `change` ввела возможности человеческой команды как критерий. В основной файл добавлено общее правило использовать реальные возможности агента и инструментов, не выдумывая ограничения человеческой разработки. Свежая попытка той же задачи прошла. Остальные Terra-ответы получены до последней правки. Sol выполнял все задачи на итоговых неизменных рабочих файлах; [их SHA-256](frozen-final-hashes.json) идентифицирует проверенную версию без цикла самоссылки на commit.

Слепая проверка четырёх проектных пар (проверяющий видел A/B без модели и условия) дала равенство по существенным гарантиям. Проверены 78 критериев во всех восьми ответах; топология, терминология и длина не заменяли корректность. Проверки продукта в проектных ответах считались предложениями. Кодовые проверки действительно запускались на сгенерированных артефактах. Все участники были независимыми свежими агентами; ожидаемые ответы и скрытые проверки исполнителям не передавались.

**Преимущество Sol по качеству здесь не обнаружено.** Обеим группам доступны одинаковые сильные инструкции среды и инженерные руководства. Это сравнение добавления данного пакета в такую среду, а не обучение модели с нуля. Один запуск на условие не оценивает устойчивость статистически. Живой выпускник курса не участвовал; источники критериев — текстовые разобранные примеры, не видео. Перенос метода не доказывает полное равенство компетенций.

Сюжеты — собственные краткие формулировки; главы курса не распространяются. Условие offline требует распознать несовместимость требований, не реализовать невозможную систему.

В следующих испытаниях сохраняйте одинаковые задачу, инструменты, доступ, инструкции среды и параметры модели. Исполнителям передавайте только задачу и, в соответствующем условии, рабочий пакет. Проверяющий получает критерии отдельно. Новые случаи нужны для независимого измерения после изменения скилла; повтор известного задания подтверждает исправление, но не перенос на новые задачи.

## Повтор кодовой проверки

Нужны Python со стандартной SQLite и установленный Rust; сеть и сторонние пакеты не требуются. Используйте отдельную временную папку. Замените обозначенные абсолютные пути на свои. Кандидат и проверка должны лежать рядом для Rust; Python получает путь через переменную окружения.

```sh
evaluation_dir='/absolute/path/to/product-engineering/evaluations/2026-11-11'
check_dir=$(mktemp -d)
cp "$evaluation_dir/operation-checks.rs" "$check_dir/operation-checks.rs"
cp '/absolute/path/to/candidate/operation.rs' "$check_dir/candidate.rs"
rustc --edition=2021 --test "$check_dir/operation-checks.rs" -o "$check_dir/operation-tests"
"$check_dir/operation-tests" root_ --nocapture
cp "$evaluation_dir/migration-checks.py" "$check_dir/migration-checks.py"
EVAL_MIGRATION_FILE='/absolute/path/to/candidate/migrate.py' python3 "$check_dir/migration-checks.py"
```

После сохранения результата удалите только созданный `check_dir`. Проверки не исчерпывают все входы и не моделируют потерю питания. Модель операции не доказывает ровно один эффект реального провайдера. SQLite может создавать служебные WAL/SHM рядом с источником; проверены сохранение данных и основного файла, автоматическое удаление потенциально общих sidecar не разрешается.

Полные исходные ответы, собственные тесты исполнителей, слепой разбор с цитатами и manifest SHA-256 переданы владельцу локально; они не входят в устанавливаемые инструкции. Следующий шаг — независимые реальные задания с учётом полной стоимости до приёмки, а не расширение скилла ради победы на этом наборе.
