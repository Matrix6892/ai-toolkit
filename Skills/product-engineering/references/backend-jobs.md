# Дополнение: долговечные фоновые задачи

Применяйте, когда операция переживает HTTP-запрос, перезапуск процесса или выполняется агентом несколько минут. Для одноразового локального скрипта весь набор может быть избыточен. Это собственный синтез по [зафиксированному источнику](sources.md), а не импорт его кода или универсальное требование DDD.

## Что забираем

| Механизм | Зачем | Что проверить |
|---|---|---|
| Сохраняемое намерение запуска и идентификатор задачи | Работа не исчезает с ответом HTTP | Принятая задача находится после остановки; судьба недоставленной работы определена |
| Контракт типа/версии, входов и результата | Старые записи можно читать после изменений | Сериализация и чтение известных/неизвестных версий сохраняют данные и объяснимый исход |
| Один владелец общих переходов выполнения | Бизнес-логика и исполнитель не спорят за status/result/error | Конкурентный захват, завершение, отмена и повтор имеют допустимый исход |
| Узкие интерфейсы хранения и запуска | Сценарий проверяется отдельно от очереди/БД/CLI | Подмена сохраняет контракт; реальные адаптеры отдельно проверены |
| Связанные события и файлы | Можно понять результат без чтения всего worker log | Артефакт относится к правильной задаче, доступен её владельцу, ошибка видна |
| Проверка границ кодом | Повторяемая формальная ошибка обнаруживается автоматически | Разрешённый импорт проходит, запрещённый действительно вызывает ошибку |

## Ключевые различия

Зарегистрирована, поставлена в очередь, выполняется и завершена — разные обязательства. Отмена запрошена не обязательно означает отменён внешний эффект. Результат сетевого вызова может быть неизвестен. Конкретные названия состояний выбирайте по продукту.

Бизнес-сценарий отвечает за предметный результат; инфраструктура запуска — за общий жизненный цикл. Формат сериализации принадлежит адаптеру. Чтение неизвестного типа не должно молча терять исходную запись.

Сохранение в БД и enqueue в другую систему обычно не одна транзакция. Разберите остановку между этими шагами, повторную доставку и ранний старт worker. Наличие состояний и очереди само по себе не даёт exactly-once — гарантии ровно одного внешнего эффекта. Нужны проверенные механизмы и конкретные сценарии восстановления.

## Что оставляем выбором проекта

FastAPI + SQLModel + Redis/ARQ, каталог `backend/app`, отдельный файл для каждой сущности/ошибки, обязательные ABC+Impl+factory и комментарии AAA — соглашения исходного проекта. Они могут быть полезны в нём, но не обязательны для других стеков или простой задачи. Не превращайте найденный checklist в требование перестроить весь продукт.

## Минимальная проверка при внедрении

Проверьте пользовательский запуск → получение идентификатора → наблюдение → результат/ошибка; значимые повтор, отмену и восстановление. Для cross-store запуска нужны сценарии отказа в конкретных точках; для доступа — чужая задача и её артефакт. Выберите фактическую БД и очередь, если гарантия зависит от них. В этой коллекции runtime исходного backend-kit не запускался.
